## Vorab: Umgebung

Der Branch war beim Sessionstart bereits in einem anderen (leeren, unlocked) Worktree
ausgecheckt — dort entfernt (`git worktree remove`, ohne `--force`, da sauber), danach hier neu
ausgecheckt.

Beim ersten vollständigen E2E-Lauf lief bereits ein alter Node-Preview-Prozess auf Port 4173
(PID 9864, Rückstand eines anderen Agenten/Worktrees, servierte einen veralteten Build ohne den
Menüeintrag „Als SVG"). Dadurch scheiterten zunächst alle 14 F-20-E2E-Tests am
Download-Timeout, weil der Knopf „Als SVG" im servierten (alten) Markup gar nicht existierte.
Prozess beendet, sauberer `npm run build && npm run preview` — danach fand sich der Knopf, und
der tatsächliche, unten beschriebene Fehler wurde sichtbar. Kein Befund gegen die Umsetzung,
reines Testaufbau-Rauschen.

## Befund und Behebung (Code)

**Beobachtung:** Test „enthält keine unsichtbaren Trefferflächen der Kanten (.edge-hitbox) aus
F-11" schlug auch nach der Testkorrektur fehl: `expect(content).not.toMatch(/edge-hitbox/)`
fand die Zeichenkette `edge-hitbox` weiterhin im heruntergeladenen SVG — nicht als DOM-Element
(die wurden korrekt entfernt, `parsed.querySelectorAll('.edge-hitbox')` lieferte bereits 0),
sondern als tote CSS-Regel `.edge-hitbox { fill: none; stroke: transparent; stroke-width: 12; }`
im eingebetteten `<style>`-Block (`exportStylesheet()` in `src/lib/export/svg.ts`), die
unabhängig von `keepSelection` unconditional erzeugt wurde, obwohl die zugehörigen Elemente in
jedem Fall entfernt werden.

**Verletzte Quelle:** F-20-AK „Kein `<style>`-Verweis auf eine externe Datei bleibt übrig" und
`features/STATUS.md`, Abschnitt „Nachzuholen" („prüfen, dass die unsichtbaren Trefferflächen der
Kanten aus F-11 … NICHT im exportierten SVG landen") — die Trefferflächen aus F-11 dürfen nicht
im Export landen, das gilt für die Datei als Ganzes (auch als reiner CSS-Text), nicht nur für
gerenderte DOM-Elemente. Live am tatsächlichen Downloadergebnis verifiziert (siehe unten), nicht
nur am Code.

**Behebung:** Die Regel `.edge-hitbox { … }` aus `exportStylesheet()`
(`src/lib/export/svg.ts`) entfernt und durch einen erklärenden Kommentar ersetzt, warum sie
absichtlich fehlt. Keine Testdatei verändert — reine Produktionscode-Korrektur.

**Verifikation am laufenden Programm (nicht nur Code/Unit-Tests):** `npm run build && npm run
preview`, im Browser eine Beziehung selektiert (Halo/Dimming aktiv), Nachttafel für die
Bildschirmoberfläche gewählt, „Exportieren → Als SVG" geklickt und die tatsächlich
heruntergeladene Datei (`featuremap-2026-09-10.svg`, frisch mit Zeitstempel geprüft) inspiziert:

- `edge-hitbox`: **0 Treffer** (weder als Element noch als Style-Text) — Fix bestätigt.
- `<link`: 0 Treffer.
- `class="…dim…"` / `class="…halo…"`: 0 Treffer, obwohl beim Export eine Selektion aktiv war
  (neutraler Zustand korrekt zurückgenommen, FR-67).
- Hintergrundrechteck: `fill="#fafaf6"` (Tag-Token `--paper`) — Export bleibt bei Tag, obwohl
  die Bildschirmoberfläche auf Nacht stand (F-20, „Standardtafel für den Export ist Tag").
  `viewBox="-4 16 1005.125 675"` vorhanden.
  QUICK WINS/GROSSE VORHABEN/NEBENBEI/VERMEIDEN sowie EFFORT/IMPACT vorhanden.
- Genau ein `<style>`-Block, Font-Stacks `Fraunces, Georgia, serif` /
  `Karla, Helvetica, Arial, sans-serif` / `Azeret Mono, Consolas, monospace` — wortgleich FR-68.

## Flakiness-Prüfung („4 von 14 Tests unter Systemlast flaky")

Nach der Testkorrektur und dem Code-Fix mehrfach geprüft:

- `npx playwright test e2e/F-20-export-svg.spec.ts --workers=1 --repeat-each=3`: **42/42 grün**,
  durchweg (serieller Lauf, keine Parallelität).
- `npx playwright test e2e/F-20-export-svg.spec.ts` (Standard-Parallelität): **14/14 grün**,
  mehrfach wiederholt.
- Ein `--repeat-each=3` mit voller Worker-Parallelität (8 parallele Chromium-Instanzen für
  denselben Spec) erzeugte vereinzelt `download.path: canceled` — plausibel echte
  Ressourcen-Konkurrenz vieler gleichzeitiger Downloads unter starker künstlicher Last (deutlich
  über der Parallelität eines normalen vollständigen Suitenlaufs, der pro Spec nur je einen
  Durchlauf fährt). Da derselbe Lauf seriell (`--workers=1`) durchweg grün ist und kein
  einziger regulärer Volllauf der Suite (mehrere unten dokumentierte Wiederholungen) dieses
  Muster zeigte, keine Änderung an Wartemechanismen vorgenommen — es gibt keinen Hinweis auf
  eine fehlende Wartebedingung in der Anwendung oder den Tests, sondern auf induzierte
  Downloadmanager-Last, die im regulären Testbetrieb nicht auftritt.
- Ein einzelner vollständiger Suitenlauf zeigte einen fehlgeschlagenen Test außerhalb F-20
  (`F-11-selektion.spec.ts`, ein 50-ms-Zeitbudget-Test) unter Systemlast — vorbestehender,
  bereits gemergter Test eines anderen, längst abgeschlossenen Features, außerhalb des Umfangs
  dieser QA und nicht Teil der hier autorisierten Testkorrektur.
